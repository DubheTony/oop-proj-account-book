## 1. 实际 CSV 格式 vs 任务文档简化格式

### 1.1 任务文档中的假设格式

```
date, amount, type, category, account, note
2025-03-15, 35.5, 支出, 餐饮, 微信, 食堂午饭
```

列名清晰、直接对应 Transaction 字段、`category` 已分类好、`account` 直接可映射。

### 1.2 微信支付实际格式

| 属性 | 值 |
|------|-----|
| 编码 | UTF-8-BOM（`utf-8-sig`） |
| 总行数 | 530（512 条交易 + 18 行元数据） |
| 元数据行 | 第 0-16 行（含昵称、时间范围、汇总统计、注释） |
| 表头行 | 第 17 行 |
| 数据起始 | 第 18 行 |
| 列数 | 11 |

**列结构**（表头行）：

| 列序 | 列名 | 示例值 | 说明 |
|------|------|--------|------|
| 0 | 交易时间 | `2026-05-01 16:31:17` | 含时间，非纯日期 |
| 1 | 交易类型 | `商户消费` `转账` `零钱提现` | 太粗，不能用做 category |
| 2 | 交易对方 | `麦当劳` `拼多多` `联系人01` | 推断 category 的主要依据 |
| 3 | 商品 | `麦当劳` `四方家居专营店APP充值` `/` | 辅助推断 category |
| 4 | 收/支 | `支出` `收入` `/` | `/` = 中性交易 |
| 5 | 金额(元) | `¥29.24` `¥2,000.00` | 带 ¥ 前缀，千位有逗号 |
| 6 | 支付方式 | `零钱通` `零钱` `某银行储蓄卡(****)` | 不用于 Transaction |
| 7 | 当前状态 | `支付成功` `已全额退款` | 不用于 Transaction |
| 8 | 交易单号 | `4500000123456789012345678901` | 不用于 Transaction |
| 9 | 商户单号 | `XP1234567890123456789012` | 不用于 Transaction |
| 10 | 备注 | `/` `服务费¥2.00` | 可选存入 note |

**交易构成**：收入 121 笔 / 支出 358 笔 / 中性 19 笔

### 1.3 支付宝实际格式

| 属性 | 值 |
|------|-----|
| 编码 | **GBK**（非 UTF-8） |
| 总行数 | 804（780 条交易 + 24 行元数据） |
| 元数据行 | 第 0-22 行（含姓名、账户、时间范围、汇总统计、特别提示） |
| 表头行 | 第 23 行 |
| 数据起始 | 第 24 行 |
| 列数 | 13（第 12 列恒为空，是尾随逗号的产物） |

**列结构**（表头行）：

| 列序 | 列名 | 示例值 | 说明 |
|------|------|--------|------|
| 0 | 交易时间 | `2026-05-01 04:07:14` | 含时间 |
| 1 | 交易分类 | `日用百货` `文化休闲` `投资理财` | 可直接映射标准类别 |
| 2 | 交易对方 | `某基金管理有限公司` `联系人01` | — |
| 3 | 对方账号 | `zfb***@example.com` `138****0000` | 微信没有此列 |
| 4 | 商品说明 | `余额宝-收益发放` `转账` | — |
| 5 | 收/支 | `收入` `支出` `不计收支` | `不计收支` = 中性交易 |
| 6 | 金额 | `0.12` `1100.00` `5000.00` | **纯数字，无 ¥ 无逗号** |
| 7 | 收/付款方式 | `余额宝` `账户余额` | — |
| 8 | 交易状态 | `交易成功` | — |
| 9 | 交易订单号 | `20260101123456789012345\t` | 可能含 tab 字符 |
| 10 | 商家订单号 | 空 或 `\t` | — |
| 11 | 备注 | 通常为空 | — |
| 12 | （空） | 恒为空 | 尾随逗号产物 |

**交易构成**：收入 38 笔 / 支出 366 笔 / 不计收支 391 笔

### 1.4 关键差异总结

| 维度 | 任务文档假设 | 微信实际 | 支付宝实际 |
|------|-------------|----------|-----------|
| 编码 | UTF-8 | UTF-8-BOM | **GBK** |
| 元数据行 | 0（直接就是表头） | 18 行 | 24 行 |
| 金额格式 | 纯数字 | `¥29.24` `¥2,000.00` | 纯数字（无 ¥ 无逗号） |
| 日期格式 | `YYYY-MM-DD` | `YYYY-MM-DD HH:mm:ss` | `YYYY-MM-DD HH:mm:ss` |
| category 字段 | 直接存在 | **不存在**，需推断 | **不存在**，需推断 |
| account 字段 | 直接存在 | **不存在**，由来源推断 | **不存在**，由来源推断 |
| 中性交易标记 | （未提及） | `收/支="/"` | `收/支="不计收支"` |

**核心结论**：解析器必须处理三种差异——**编码差异、元数据行差异、字段映射差异**。不能用一个统一的简单 CSV Reader 搞定。

## 2. 解析流程设计

```
┌──────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐     ┌────────────────┐
│ CSV 文件 │ ──→ │ 1. 格式检测   │ ──→ │ 2. 定位表头   │ ──→ │ 3. 逐行解析   │ ──→ │ 4. 返回结果     │
│   (path) │     │ 微信/支付宝/? │     │ 跳过元数据行   │     │ 过滤+映射+构建  │     │ (transactions, │
└──────────┘     └──────────────┘     └──────────────┘     └──────────────┘     │  skipped_count) │
                    │                                                            └────────────────┘
                    │ 异常
                    ▼
              ┌────────────┐
              │ 抛出错误    │
              │ 上层处理    │
              └────────────┘
```

### 2.1 步骤 1：格式检测

**策略**：先试 UTF-8-BOM 编码打开，扫描前几行找特征字符串；失败则试 GBK。

```
判定规则：
  前 6 行中出现 "微信支付账单明细"  →  wechat
  前 6 行中出现 "支付宝交易明细"    →  alipay
  以上皆无                         →  异常
```

**异常处理**：

| 异常场景 | 原因 | 处理方式 |
|----------|------|----------|
| `UnicodeDecodeError`（两种编码均失败） | 文件非 UTF-8 也非 GBK | 捕获后抛出 `ValueError("无法解码文件，支持的编码: UTF-8, GBK")` |
| 特征字符串未匹配 | 非微信/支付宝导出文件 | 抛出 `ValueError("无法识别的CSV格式，支持的格式: 微信支付账单导出、支付宝交易明细导出")` |
| 文件为空（0 字节） | 空文件 | 抛出 `ValueError("CSV文件为空")` |

### 2.2 步骤 2：定位表头

不硬编码行号（可能因微信/支付宝版本更新而变化）。改为检测表头行特征：

- 表头行第 0 列内容为 `交易时间`
- 检测到后，下一行开始即为数据

**异常处理**：

| 异常场景 | 处理方式 |
|----------|----------|
| 文件中找不到表头行（如只有元数据、被截断） | 返回空列表 `([], 0)`，不抛异常 |

### 2.3 步骤 3：逐行解析

**微信映射逻辑**：

```
CSV 列 → Transaction 字段：
  交易时间(0)  →  date     （解析 YYYY-MM-DD HH:mm:ss → date 对象）
  收/支(4)     →  type     （"收入"/"支出" 直接使用）
  金额(元)(5)  →  amount   （去掉 ¥ 和逗号 → float）
  交易对方(2)  →  (用于推断 category)
  商品(3)      →  (用于推断 category) + note
  备注(10)     →  note
  
  account      →  固定为 AccountType.WECHAT
  
  过滤规则：
    收/支(4) == "/"  →  跳过（中性交易，如提现、零钱通互转）
```

**支付宝映射逻辑**：

```
CSV 列 → Transaction 字段：
  交易时间(0)  →  date     （解析 YYYY-MM-DD HH:mm:ss → date 对象）
  收/支(5)     →  type     （"收入"/"支出" 直接使用）
  金额(6)      →  amount   （纯数字 → float）
  交易分类(1)  →  (用于推断 category)
  商品说明(4)  →  note
  
  account      →  固定为 AccountType.ALIPAY
  
  过滤规则：
    收/支(5) == "不计收支"  →  跳过
    类别映射返回 None（投资理财/退款/账户存取）→  跳过
```

**单行异常处理**（每行独立 try/except，不中断整体导入）：

| 异常场景 | 处理方式 |
|----------|----------|
| 列数不足 | `print("[CSV] 第{i}行跳过: 列数不足")`，skip+1 |
| 日期解析失败 | `print("[CSV] 第{i}行跳过: 无法解析日期: {raw}")`，skip+1 |
| 金额非数字 | `print("[CSV] 第{i}行跳过: 金额格式错误: {raw}")`，skip+1 |
| 其他 ValueError/KeyError | `print("[CSV] 第{i}行跳过: {e}")`，skip+1 |

### 2.4 步骤 4：返回结果

```python
返回：(transactions: list[Transaction], skipped_count: int)
打印汇总：[CSV] {文件名}: 导入完成 — {成功数} 条成功, {跳过数} 条跳过
```

## 3. 类别标准化策略

### 3.1 标准类别定义（6 类）

```
餐饮   — 吃饭、外卖、聚餐、零食、饮料
交通   — 公交、地铁、打车、高铁、共享单车
娱乐   — 电影、游戏、KTV、旅游、运动、演出
学习   — 书籍、文具、课程、打印、考试
日用   — 超市、日用品、话费、衣服、网购、美妆、水电
其他   — 医疗、礼物、红包、转账、快递、以及所有无法归类项
```

### 3.2 支付宝：字典映射（直接且有结构）

支付宝的 `交易分类` 字段本身就是类目体系，与我们的 6 标准类别有较清晰的对应：

```
支付宝交易分类 → 标准类别：

  餐饮美食           →  餐饮
  交通出行           →  交通
  爱车养车           →  交通
  文化休闲           →  娱乐
  酒店旅游           →  娱乐
  运动户外           →  娱乐
  教育培训           →  学习
  日用百货           →  日用
  数码电器           →  日用
  服饰装扮           →  日用
  家居家装           →  日用
  生活服务           →  日用
  美容美发           →  日用
  充值缴费           →  日用
  住房物业           →  日用
  医疗健康           →  其他
  母婴亲子           →  其他
  商业服务           →  其他
  快递物流           →  其他
  转账红包           →  其他
  收入               →  其他
  其他               →  其他

  投资理财           →  跳过（非消费/收入）
  退款               →  跳过
  账户存取           →  跳过
```

支付宝的优势：分类体系完善，映射歧义少。少数未覆盖的分类自动归入"其他"。

### 3.3 微信：关键词推断（粗粒度，需启发式规则）

微信的 `交易类型` 字段太粗（大部分是"商户消费"）。**必须从商户名和商品描述中推断类别。**

**推断方法**：维护一个关键词→类别的规则表，按以下优先级匹配：

1. **商户名匹配**（精确度较高）— 如"麦当劳"→餐饮、"拼多多"→日用
2. **商品描述匹配**（辅助）— 如"外卖"→餐饮、"公交"→交通
3. **以上均不匹配** → 归入"其他"

**规则表示例**（需根据实际 CSV 数据不断扩充）：

```
商户名含 "麦当劳"/"蜜雪冰城"/"正新鸡排"/"隆江猪脚饭"/... →  餐饮
商户名含 "滴滴"/"高德"/"哈啰"/...                        →  交通
商户名含 "拼多多"/"京东"/"淘宝"/"天猫"/...                 →  日用
商户名含 "金源文具图书专营店"/"新华书店"/"知网"/...                      →  学习
商户名含 "Steam"/"猫眼"/"大麦"/"迪士尼"/...                →  娱乐
商品含 "外卖"/"食堂"/"套餐"                                →  餐饮
商品含 "公交"/"地铁"/"高铁"                                →  交通
...
全部不匹配                                                →  其他
```

**推断准确率取决于规则表的覆盖度**。首次导入后，"其他"类别中的交易需要人工复查。

### 3.4 未匹配类别的处理（关键设计点）

这是类别标准化中最实际的问题：映射表和规则表不可能覆盖所有情况。

**设计思路**：

```
导入阶段（自动）              复查阶段（手动）              复用阶段
───────────────          ───────────────          ──────────────
                         
CSV 解析                   用户在 CLI/GUI 中        修正后的映射
  │                        查看 "其他" 列表          保存为自定义规则
  ├─ 匹配成功 → 归类        │                       ↓
  │                          ├─ 逐条修正类别         下次导入时
  └─ 未匹配   → "其他"      │                      自动应用
                             ├─ 或：批量选择          
                             同一商户的全部交易        
                             一键改类别              
                             │
                             └─ 保存为规则
```

**逐步细化**：
1. **初次导入**：用预设规则表，大量未知商户归入"其他"
2. **人工复查**：在 CLI/GUI 中查看"其他"类别的交易，手动修正
3. **规则沉淀**：修正结果保存为自定义映射（如 JSON 文件 `custom_category_rules.json`）
4. **后续导入**：合并"预设规则 + 自定义规则"，匹配率逐步提升

这与任务文档中的描述一致：*"实际映射表可以根据 CSV 数据中的实际类别名扩充。你和组员一起看一遍 CSV 后补充。"*

## 4. 与 FinanceController 的接口约定

### 4.1 csv_importer 对外接口

```python
# services/csv_importer.py

def import_csv(path: str) -> tuple[list[Transaction], int]:
    """
    自动检测 CSV 格式（微信/支付宝），解析并返回交易列表。

    参数:
        path: CSV 文件路径

    返回:
        (transactions, skipped_count)
        - transactions: 成功解析的 Transaction 列表
        - skipped_count: 跳过的行数（含格式错误 + 中性交易过滤）

    异常:
        ValueError: 无法识别的 CSV 格式
        FileNotFoundError: 文件不存在
    """
```

### 4.2 FinanceController 调用方式

```python
# services/finance_controller.py (C 同学负责)

def import_csv(self, path: str) -> int:
    """
    导入 CSV 文件中的所有交易。
    每条交易通过 add_transaction() 加入，触发预算更新和预警检查。
    """
    from services.csv_importer import import_csv as parse_csv

    transactions, skipped = parse_csv(path)

    for t in transactions:
        self.add_transaction(t)  # 内部处理预算更新 + 预警

    if skipped > 0:
        print(f"[Controller] CSV导入: {len(transactions)}条成功, {skipped}条跳过")

    return len(transactions)
```

### 4.3 依赖关系

```
csv_importer.py 依赖:
  ├── models.transaction (Transaction, AccountType)   ← 来自 C
  └── services.category_normalizer (normalize_*)       ← 来自 B 自己

csv_importer.py 不依赖:
  ├── FinanceController
  ├── 任何 Strategy / Rule / Method
  └── GUI 代码
```

**csv_importer 是纯函数**：输入文件路径 → 输出数据列表。不维护状态、不持有 Controller 引用。

## 5. 错误处理总览

```
层级                      错误类型                    处理策略
─────────────────────────────────────────────────────────────────
文件级                    文件不存在                   FileNotFoundError → 上层处理
                          格式无法识别                 ValueError → 上层处理
                          编码错误（两种均失败）        ValueError → 上层处理
                          空文件                       ValueError → 上层处理
─────────────────────────────────────────────────────────────────
行级（单行不中断整体）     列数不足                     print 警告 + skip
                          日期解析失败                 print 警告 + skip
                          金额非数字                   print 警告 + skip
                          商户/类别映射异常             print 警告 + skip
─────────────────────────────────────────────────────────────────
静默过滤（不算 skip）      中性交易（收/支="/"）       静默跳过
                          中性交易（不计收支）          静默跳过
                          投资理财/退款/账户存取       静默跳过
─────────────────────────────────────────────────────────────────
数据级                    纯元数据无交易行              返回空列表 (不抛异常)
                          导入后"其他"类别过多          人工复查（非错误）
```
